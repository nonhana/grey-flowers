# Grey Flowers 后台运营工作流切片

## 状态与用途

- 决策日期：2026-08-02
- 状态：完整后台项目的实施拆分已确认
- 文档类型：架构说明与交付边界
- 读者：后续实现 Admin、API、主站资源迁移与验收的维护者

本文将 Grey Flowers 后台拆分为能够独立完成、独立验收并按顺序交付的运营工作流。它服务于一个完整后台项目：项目完成时，后台必须覆盖当前主站的全部运营需求；不得将任何既定需求降级为可选工作。

“切片”只表示实施与迁移顺序。每个切片完成后都必须处于可用状态，不等待后续切片补齐其规则、界面或数据写入路径。后续切片可以扩展已存在的能力，但不得修复前一切片故意留下的功能缺口。

本文以前置的 [Admin 技术栈设计](./2026-08-01-admin-technology-stack.md)、[四个项目的身份定位](./2026-08-01-four-project-roles.md)、[React Frontend 架构设计](./2026-08-01-react-frontend-architecture.md)、[Hono Backend 架构设计](./2026-08-01-hono-backend-architecture.md) 与 [Prisma 领域模型参考](./prisma-domain-model-reference.md) 为约束。发生冲突时，以这些文档已经确定的项目职责、依赖方向和数据边界为准。

本文不授权直接创建路由、DTO、数据库迁移、对象存储配置或部署变更。每个切片仍须先形成相应的专项设计与实施任务。

## 完整覆盖目标

后台是唯一的运营与数据管理工作台。完成全部切片后，管理员能够完成当前主站所需的内容、媒体、互动与用户运营操作；`apps/api` 成为这些资源的唯一业务访问入口，`apps/admin` 与 `apps/main` 均通过 API 使用业务数据。

旧 `nuxt-admin` 是行为与体验证据，不是实现来源。每个切片开始时，维护者必须建立行为清单，将旧项目和当前主站的相关行为逐条标为：

- **采纳**：以新架构实现相同的用户结果；
- **调整**：保留用户目标，但以新的权限、合同或交互实现；
- **拒绝**：明确记录不保留的原因与替代路径。

不得复制旧项目的 Nuxt API、Prisma 直连、页面内 DTO、表单校验或业务规则。不得因缺少实现细节而静默遗漏当前需求。

## 工作流切片的判定标准

一个工作流切片必须同时满足以下条件：

1. **明确的运营结果**：管理员能从一个清晰的起点完成一次日常任务，例如“安全上传并管理一个资产”或“发布一篇文章”。
2. **独立的规则边界**：该任务的权限、状态迁移、关系一致性和事务边界归属明确，不由浏览器或后续切片补充判断。
3. **完整的跨层闭环**：具备稳定的 Zod 输入/输出 DTO 与错误码、Hono 用例、响应式 Admin 界面和可验证的成功与失败结果。
4. **可独立迁移**：对应资源的 Admin/Main 调用方已迁移到 API；遗留的 Prisma 读写、业务端点和常态双写路径已关闭。
5. **可独立验收**：行为清单、权限验证、错误与边界条件、窄屏操作和迁移后的主站行为都有可追溯证据。

Prisma model 是识别数据归属的线索，不是切片数量的计数器。关联表、投影和内部消息只有在形成独立运营任务时才成为一级切片。

## 横切前置条件

认证、会话、Principal、管理员授权、CORS、CSRF 和统一错误映射是所有管理写操作的前置条件。它们不单独构成一个没有运营结果的切片；其设计和最小实现必须随“受管理资产”切片一并完成，因为资产创建要记录创建者且必须拒绝未授权访问。

在首个受保护用例编码前，专项设计必须明确：

- 管理员如何登录、续期、退出和恢复会话；
- API 如何从请求建立 Principal，并如何区分 `ADMIN` 与普通用户；
- 跨域、CSRF 与凭据传递如何配合部署拓扑；
- 调用方如何根据统一错误合同展示认证、权限与可恢复失败；
- 当前主站的相关认证与写入路径如何迁移和关闭，而不是与 API 长期平行运行。

## 切片之间的边界

### 受管理资产先于内容与媒体工作流

`Asset` 的对象归属、存储 key、生命周期和失败补偿属于独立的业务结果。文章封面、正文插图、动态图片、音乐音源和音乐封面都依赖这个结果，因此不得在文章、动态或音乐页面中各自临时实现上传、删除或对象清理逻辑。

R2 Adapter 只处理真实的对象存储差异；授权、用途选择、文件校验、数据库记录与补偿仍属于 Asset 用例。若上传协议或对象存储边界尚未确定，必须在切片专项设计中确定后再实现，不能以浏览器直连或临时 URL 绕过 API。

### 内容发布合并文章、标签与分类

文章工作台天然需要选择分类、标签和资产；文章新建、更新、发布与删除会影响这些关系及其运营展示。将 `Tag` 或 `Category` 拆成独立的纯 CRUD 项目，会让内容发布无法形成完整闭环。

`ArticleInlineAsset` 不单列切片。它是文章正文中受管理资产引用的一部分，必须与 Markdown/MDC 的明确引用语义和文章保存事务一同实现。普通外部 URL 继续保持可表达，不能被后台静默重写为受管理资产。

文章自动保存、离线恢复、冲突处理和版本历史都属于内容发布工作流，而不是可无限期延后的体验选项。它们的并发前置条件、快照模型和恢复语义必须在内容发布切片的专项设计中明确，并在该工作流完成前实现。

### 音乐库与动态发布分开交付

音乐可以独立存在，`Music.activityId` 也允许为空；管理员应能先管理音乐库，再在动态中选择它。因此音乐库和动态发布是两个独立任务：前者拥有音频与元数据，后者拥有动态正文、图片排序和可选音乐关联。

`ActivityImageAsset` 不单列切片。它是动态图片的排序关系，随动态发布工作流一起校验和维护。

### 评论、用户与概览各自承担不同任务

评论处置面向评论树和互动结果，关联作者不等于用户管理。用户运营面向资料、互动历史和管理员权限边界；它不复制评论处置规则。`UserMessage` 没有一级页面，除非未来已经证实存在独立且日常的消息运营任务。

运营概览没有独立 Prisma model。它只能读取已经完成的领域用例，不能抢占文章、资产、评论或用户的写入职责，也不能为了统计而创建第二份业务状态。

## 每个切片的交付闭环

每个切片的专项设计与实施必须按以下闭环完成：

1. 建立旧后台与当前主站的相关行为清单，并记录采纳、调整或拒绝结论。
2. 定义角色、权限、状态、关系一致性、事务边界和不可恢复操作的确认语义。
3. 在 `packages/contracts` 定义输入 DTO、成功 DTO、可处理错误码和失败表示；不得暴露 Prisma 类型。
4. 在 `apps/api` 实现对应 Hono 模块、DTO 映射和业务编排；路由保持薄，业务规则不进入 Admin 或 Main。
5. 在 `apps/admin` 实现同一工作流的桌面、平板和手机操作语义，包括加载、空状态、失败、重试和危险操作确认。
6. 将该资源的 `apps/main` 调用方迁移到 API，验证 SSR 与浏览器行为，并删除遗留的 Prisma 读写和业务端点。
7. 记录自动化检查与人工验收证据，至少覆盖成功、权限拒绝、校验失败、关系/生命周期边界和窄屏操作。

切片未完成上述闭环时，不能以“接口已写”或“页面已存在”宣称交付完成。

## 明确不在本文决定的事项

本文不决定以下实现细节；每项必须在首次依赖它的工作流专项设计中确定：

- 登录、会话、CSRF、CORS、Principal 和管理员授权的具体协议；
- R2 上传方式、大小与 MIME 限制、对象命名、媒体元数据提取和清理作业；
- API 路由命名、HTTP 状态码细则与 DTO 字段；
- 文章版本快照的数据模型、自动保存节流、离线恢复与冲突策略；
- Admin 路由、请求缓存、复杂表单库、部署域名与预览环境；
- 任何超出当前主站运营需求的新产品能力。

这些待定项不能改变完整覆盖目标、七个工作流边界或 API 为唯一业务入口的约束。
